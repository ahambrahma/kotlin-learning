# Rate Limiting with Ktor — Theory

Read this once before touching the TODOs. Every module so far has been a plain `fun main()`
console program. This one is the first real HTTP *server* - Ktor - and the actual subject matter
is a token bucket rate limiter wired in as request-intercepting middleware (Ktor calls these
"plugins"). Four things to get right: the token bucket algorithm itself, how Ktor's plugin
mechanism actually controls whether a request reaches your routes, keeping the shared bucket state
safe under real concurrent requests, and designing the storage layer so it isn't welded to
"in-memory" forever.

## 1. The token bucket algorithm, precisely

A bucket has a **capacity** (max tokens it can hold) and a **refill rate** (tokens added per
second). Every incoming request tries to take one token. If a token is available, the request is
allowed and a token is removed. If not, the request is rejected (`429 Too Many Requests`). Tokens
regenerate continuously at the refill rate, up to the capacity ceiling.

The subtlety is *how* refilling actually happens. You are **not** running a background timer that
wakes up every N milliseconds to add tokens - that's wasteful (a thread/coroutine per bucket doing
nothing most of the time) and doesn't scale to many independent buckets. Instead, refilling is
**lazy**: every time a request arrives, you first compute how much time has elapsed since the last
time this bucket was touched, convert that elapsed time into "how many tokens would have
regenerated by now," add that (capped at capacity), and *then* check whether there's a token to
give out. Concretely, with a bucket of capacity 5 and a refill rate of 1 token/second, currently
sitting at 0 tokens: if the next request arrives 3.2 seconds later, you first add `3.2 * 1 = 3.2`
tokens (now at 3.2, still under the cap of 5), then check if `3.2 >= 1` - yes, so the request is
allowed and the bucket drops to `2.2`.

Use `System.nanoTime()` for this elapsed-time math, never `System.currentTimeMillis()`.
`currentTimeMillis()` reads the system's wall-clock, which can jump - forward or backward - if the
OS resyncs it against an NTP server mid-request. A backward jump would make your elapsed-time
calculation negative, which would either under-refill or throw off your math entirely.
`nanoTime()` is explicitly documented to be monotonic (only usable for measuring *elapsed* time
between two calls on the same JVM, never as a wall-clock timestamp) - exactly the property this
algorithm needs and the only property it needs.

Notice that `TokenBucket` itself, as scaffolded, has no locks or synchronization anywhere. That's
deliberate, not an oversight - see section 3.

## 2. Ktor plugins: what actually stops a request from reaching your route

Ktor's request handling is a **pipeline**: a fixed sequence of phases a call passes through -
`Setup`, `Monitoring`, `Plugins`, `Call`, `Fallback` - in that order. Routing (matching a URL to
your `get("/ping") { ... }` handler) happens during the `Call` phase, which comes *after*
`Plugins`. That ordering is exactly why a rate limiter belongs in the `Plugins` phase: it needs to
run and potentially reject the request *before* routing ever gets a chance to run your handler.

Ktor actually offers two different APIs for writing a plugin, and the choice matters a lot for a
rate limiter specifically:

- The **simplified DSL** (`createApplicationPlugin { onCall { call -> ... } }`) is what most Ktor
  documentation leads with, and it's genuinely nicer for things like appending a response header
  or logging - but it gives you the `ApplicationCall`, not the raw pipeline machinery. There is no
  way to tell it "stop here, don't continue to routing." Whatever you do inside `onCall`, the call
  always continues on to the `Call` phase afterward.
- The **Base API** (`BaseApplicationPlugin` + `pipeline.intercept(phase) { ... }`, what
  `RateLimiterPlugin.kt` is built on) gives you the actual `PipelineContext`, which exposes
  `proceed()` - a suspend function that resumes the pipeline and lets it continue to the next
  phase. Critically, if your intercepted block *doesn't* call `proceed()`, the pipeline simply
  never continues past that point for this call - routing never runs, your route handler never
  executes. That's the whole mechanism: **not calling `proceed()` is what "rejecting" a request
  actually means** at the pipeline level. When you *do* want the call to continue (the request was
  allowed), you have to call `proceed()` yourself - the Base API never does this for you
  automatically, unlike the simplified DSL.

This is why TODO 3 asks you to respond with `429` and *skip* `proceed()` on rejection, but call
`proceed()` explicitly on success. Forgetting the success-path `proceed()` call is an easy, very
visible mistake to make once and never make again: every single request just hangs forever,
because nothing ever reaches your routes, even the requests that should have been let through.

## 3. Keeping the shared bucket state safe under real concurrency

Multiple requests for the same client key can genuinely arrive at the same instant on Ktor's
multi-threaded engine (Netty). That's `kotlin-shared-state` all over again: a `TokenBucket`'s
`tryConsume()` reads `availableTokens`, computes a new value, and writes it back - a
read-modify-write with no atomicity guarantee if two threads call it on the *same instance* at the
same time.

The fix isn't to make `TokenBucket` itself thread-safe. It's to make sure only one caller at a
time can ever be inside a given bucket's `tryConsume()` in the first place - which is exactly what
`InMemoryRateLimiterStore`'s `Mutex` is for (TODO 2). This mirrors the separation
`kotlin-shared-state` drew between "the raw counter" and "the safe wrapper around it": the
algorithm class stays simple and unsynchronized, and a single, deliberate layer above it owns the
concurrency-safety concern. Putting a lock inside every low-level data structure "just in case"
is usually the wrong call - it's slower even when only ever accessed by one caller at a time, and
it spreads the "is this safe?" question across every class instead of answering it once, clearly,
at the boundary that actually needs it.

One deliberate simplification worth naming: `InMemoryRateLimiterStore` uses a single `Mutex` for
*all* keys, not one lock per key. That means a request for client "alice" and a request for client
"bob" briefly serialize against each other even though their buckets are logically independent -
correct, but not maximally concurrent. A per-key-lock design would fix that, at the cost of needing
to manage a whole map of locks instead of one - a real scalability refinement, but out of scope
here; one global `Mutex` is more than adequate at this module's scale, and the tradeoff is worth
knowing about rather than solving today.

## 4. Designing for a swappable backing store

The `RateLimiterStore` interface (given, in `RateLimiterStore.kt`) is the entire point of the
"swappable" half of this module's title, and it costs almost nothing to get right: `TokenBucket`
and `InMemoryRateLimiterStore` never appear anywhere near `RateLimiterPlugin`'s actual logic -
only the interface type does (`RateLimiterPlugin.Configuration.store: RateLimiterStore`). If a
later version of this service needed rate limits to survive a restart, or to be shared correctly
across multiple server instances behind a load balancer (where each instance holding its own
in-memory map would let a client get `N × capacity` requests through instead of `capacity`), the
fix is writing one new class - a `RedisRateLimiterStore`, say - that implements the same
`suspend fun tryConsume(key: String): Boolean` contract, and swapping which one gets passed to
`install(RateLimiterPlugin) { store = ... }`. Nothing else in the plugin, the routes, or the rest
of the application would need to change. That's the concrete payoff of programming against an
interface instead of a concrete class at this boundary - not an abstract principle, but a specific
future change this design already absorbs for free.

## Java-8 / Go callouts

- Ktor itself has no Java 8 analog worth naming - Spring MVC/WebFlux are the closest Java
  ecosystem equivalents, but the pipeline-of-phases-with-explicit-`proceed()` model is closer in
  spirit to Express/Koa-style middleware (`next()`) than to a Spring filter chain.
- The token bucket algorithm is language-agnostic - if you've built rate limiting in Go, you've
  likely reached for `golang.org/x/time/rate`, which implements this exact algorithm (it's
  literally called `rate.Limiter` and uses the same lazy-refill technique). The only new part here
  is wiring it into Kotlin's coroutine-based concurrency instead of Go's goroutines+channels.
- `System.nanoTime()`'s "monotonic, elapsed-time-only" contract is the same idea as Go's
  `time.Since(start)` being built on a monotonic clock reading since Go 1.9 - both exist to solve
  the exact same wall-clock-can-jump problem.
